# Follow-ups from the native changes and the Jev guard

Recorded on 2026-10-02 for stage 4 of the Rust port (archive, unarchive, delete, rename, title, project, memory and the Jev guard). Each is left as is for now; "verified" means observed or read, not reproduced in a user journey.

- **Resolved in stage 5.** Long chats in the Jev guard: the guard now summarises a long chat as the TS CLI does (Codex or Claude, or their APIs), with the question before a large batch (`crates/cli/tests/classify_cli.rs`; `parity_classify.rs` in tag v0.1.5).
- Changes and sync passes no longer interleave (`Syncer::exclusive`), so a pass can't write back a chat's state from before a change. The cost: a change waits for a running pass (seconds usually); the heartbeat keeps the client waiting.
- ~~While the bridge exists, the TS index learns of native changes only at its own sync, every 15 minutes: until then a bridged `review` or `tui` can still show a chat the Rust CLI deleted or archived. A deleted active chat leaves the TS index only at a TS full sync. Verified by reading.~~ Gone with the bridge.
- ~~Rate-limit notes ("rate limited by ChatGPT; waiting 5s") reach a waiting `sync`, but not a waiting change: the HTTP client's retry note goes to the daemon's shared reporter. The change still waits and retries; the note is only in the daemon's log. Verified by reading `crates/daemon/src/session.rs`.~~ Fixed after 0.2.0: each request carries its own reporter for the HTTP client's retry notes (`a_change_hears_the_rate_limit_it_waits_on`).
- Failure lines say `404 Not Found from /backend-api/…` where the TS CLI says `404 from /backend-api/…: <response body>`, and TypeSafe errors say `TypeSafe answered 401 (check the Jev API key …)` where the SDK quotes the body. No bodies, by rule. Intentional.
- A batch read in the guard that returns a chat whose transcript can't be rendered fails only that chat; the TS CLI fails the whole batch of ten. Verified by reading `src/classify/pipeline.ts`.
- Exit codes: invalid input (a bad filter, an unknown id, `--check` on unarchive, a project name in use) exits 2, as every native command's does, where the TS CLI exits 1. Every failure is still non-zero.
- Prompt without a terminal: the TS CLI fails opening `/dev/tty` with Node's error; the Rust CLI says it can't read an answer and to pass `-y`. Intentional.
- The guard's TypeSafe client honours `TYPESAFE_BASE_URL` in debug builds only (tests), and always uses `jev-latest`: the SDK also reads `TYPESAFE_BASE_URL` and `TYPESAFE_DEFAULT_MODEL` from the environment. Release builds never send the key anywhere but api.typesafe.ai. Intentional.
- `delete` of a chat not in ChatGPT counts as done and drops it from the index, as the TS CLI does; `DELETE /backend-api/conversation/id/{id}` is the TS CLI's endpoint, verified live by the TS CLI earlier, not by this port (the live demo only previews deletes).
- A chat named twice among explicit ids (`delete a a`, or a prefix and its full id) is previewed and changed once, where it first appears. The TS CLI's `selectTargets` keeps duplicates, so it previews the chat twice and sends the write twice (a second delete answers 404 and counts as done). Deliberate: safety over parity. The parity harness doesn't name a chat twice for these commands (`project add` dedupes in both).
- **Resolved in stage 5.** The Jev guard's saves take the pass lock, and it re-checks each chat's `update_time` before approving it: a chat that changed during the check is held back.
